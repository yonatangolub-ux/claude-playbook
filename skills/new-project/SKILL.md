# פרויקט חדש לפי השיטה

השיטה של המשתמש חיה בריפו GitHub בשם `claude-playbook`, אצל אותו בעלים כמו הריפו הנוכחי (אם לא ברור, `yonatangolub-ux/claude-playbook`). הסקיל הזה הוא שלבים 0 ו-1 של השיטה: הגדרה, ואז ראיון ותוכנית. הוא נגמר כש-SPEC.md מלא. **לא כותבים קוד בסשן הזה.** הבנייה (שלב 2) מתחילה בסשן נקי, כי סשן ראיון ארוך ממלא את זיכרון העבודה, וקוד שנכתב אחריו יוצא גרוע יותר.

המשתמש לא מתכנת. לדבר איתו בעברית פשוטה, להסביר מונח טכני במילה אחת כשהוא מופיע, ולא להציף אותו בשאלות.

## 1. לוודא שזה באמת פרויקט חדש

- אם הריפו הנוכחי הוא `claude-playbook` עצמו, לעצור: צריך ריפו נפרד לפרויקט. להסביר בקצרה איך יוצרים ריפו ריק ב-GitHub ולחכות.
- אם כבר יש בריפו `SPEC.md`, זה לא פרויקט חדש. לשאול אם להמשיך את הקיים במקום.
- אם המשתמש הזכיר פרויקט פעיל אחר שעוד לא עבר את מבחן ההצלחה שלו, להזכיר פעם אחת את חוק "פרויקט פעיל אחד" מ-METHOD.md, ולהמשיך לפי מה שהוא מחליט. זו החלטה שלו.

## 2. שלב 0: שלוש שורות

צריך את שלושת אלה לפני כל דבר אחר:
1. **הבעיה במשפט אחד.**
2. **מבחן הצלחה** שאפשר לענות עליו בכן או לא, במצב אמיתי. "שיהיה נוח" זה לא מבחן. "ביום X, תוך 10 שניות, בלי Y, אני רואה Z" זה מבחן.
3. **רשימת "לא עכשיו"**, כולל החלק הכי מלהיב.

אם המשתמש כבר כתב אותם, להשתמש בהם. אם חסר משהו, לבקש רק את מה שחסר. אם המבחן מעורפל, להציע ניסוח מדיד אחד ולשאול אם הוא נכון. למה זה חשוב: בלי מבחן כל רעיון נראה חשוב באותה מידה, והגרסה הראשונה מתנפחת.

## 3. להביא את השיטה

לקרוא מ-`claude-playbook` את `METHOD.md` ואת חמשת הקבצים שב-`template/`: `CLAUDE.md`, `SPEC.md`, `NOTES.md`, `frictions.md`, `IDEAS.md`. כל דרך שעובדת בסשן הזה טובה:
- בסשן ענן של Claude Code: לחבר את הריפו עם `add_repo` (גישת קריאה מספיקה), לשכפל אותו לתיקייה ליד הריפו הנוכחי, ולקרוא משם.
- כלי GitHub (`get_file_contents`) או שכפול רגיל עם git.

לא לנחש את תוכן הקבצים מהזיכרון. אם אי אפשר להגיע לריפו, להגיד למשתמש מה חסום ולעצור.

## 4. להעתיק את התבנית

להעתיק את חמשת הקבצים לשורש של הריפו הנוכחי. קובץ שכבר קיים לא דורסים: מראים למשתמש ושואלים. `README.md` שנוצר אוטומטית עם הריפו אפשר להשאיר.

## 5. שלב 1: ראיון ותוכנית

לעבוד במצב תכנון: לחשוב ולהציע, בלי קוד.
1. לשאול את השאלות שחסרות כדי לבנות את הגרסה הכי קטנה שעוברת את המבחן. בדרך כלל 3 עד 5, ולא יותר מ-3 בבת אחת. שאלות טיפוסיות: על איזה מכשיר זה רץ? איפה נשמר המידע? איך המידע נכנס? מי עוד משתמש? הריפו ציבורי או פרטי?
2. להציע תוכנית לגרסה 1, בחלקים ממוספרים. ליד כל חלק לכתוב איך הוא משרת את המבחן. להזמין את המשתמש למחוק חלקים, ולתמוך במחיקה: חלק שלא משרת את המבחן עובר ל"לא עכשיו".
3. אחרי שהמשתמש מאשר, למלא:
   - **`SPEC.md`**: הבעיה, מבחן ההצלחה, "לא עכשיו", מה בגרסה 1, ואיך בודקים שזה עובד (בדיקות אוטומטיות, ואיך בודקים את המבחן בשטח).
   - **`CLAUDE.md`**: את "חוקים של הפרויקט הזה" ואת "איך מריצים", לפי מה שהוחלט. אם הריפו ציבורי, להוסיף חוק מפורש: שום מידע אישי בריפו, גם לא ב-NOTES או ב-frictions, ובדיקות עם מידע מזויף בלבד. לשמור על הקובץ קצר: קובץ ארוך גורם להתעלם מחצי מהחוקים.
   - **`IDEAS.md`**: כל מה שנזרק מהתוכנית, ושאר הרעיונות שעלו בראיון.

## 6. לסגור את הסשן

1. ב-`NOTES.md`: שורה עם תאריך ("שלב 1: SPEC מוכן"), ושורת "הבא:" שאומרת לפתוח סשן חדש ולבנות את גרסה 1 לפי SPEC.md, עם בדיקות.
2. commit עם הודעה ברורה, ו-push לענף שהסשן עובד עליו. בסשן ענן, מה שלא נדחף נעלם.
3. לסיים בהודעה קצרה למשתמש: מה מבחן ההצלחה, מה בגרסה 1 במשפט, ומה המשפט שכדאי לפתוח בו את הסשן הבא. למשל: "תקרא את SPEC.md ו-NOTES.md ותבנה את גרסה 1."

אם הראיון התארך והמשתמש עייף, עדיף לעצור עם SPEC חלקי ושורת "הבא:" ברורה, מאשר לדחוף עד הסוף. זה שלב 7 בתבנית הסשן ב-METHOD.md: עוצרים כשהכל עובד, לא באמצע.
